Other figures from this run against the same baseline: first frame with an empty profile 401.29 ms -> 367.60 ms (warm 311.86 ms -> 279.44 ms), RSS idle with one tab 94.3 -> 99.4 MiB, with ten tabs 153.5 -> 162.0 MiB (the chrome keeps a copy of its last paint and a snapshot, and the shadow / gradient / stylesheet caches are bounded).

**The targets are met for sustained typing** (1x p50 4.63 ms, p99 7.52 ms; 2x p50 6.33 ms).

What changed (all of it produces bit-identical pixels to a full paint; `internal/engine/paint_golden_test.go` pins 1x/2x full paints of every UI scenario to hashes recorded before the change and compares each incremental repaint with a full paint): the engine compares the display list of the new paint with the previous one (content + enclosing clip/layer context per op, Myers diff) and repaints only the rows the difference can reach, starting from a cached snapshot of the part of the page that did not change; box-shadow coverage, gradient tiles and parsed stylesheets are cached; the box blur, bilinear image copy, rectangle fills and clip rectangles got fast paths that produce the same bytes; the SVG cascade is indexed.

## How to compare with Chrome

`bench/gui_vs_chromium.sh` (or the Chromium section above, which this program runs when a Chromium binary is found) launches headless Chromium on the same local fixture pages and records (a) wall time from exec to a finished `--screenshot`, and (b) peak resident and proportional (PSS) memory summed over the whole process tree with 1 and 10 tabs open. Chromium is multi-process, so a single-process RSS is not comparable; PSS summed over the tree is the fair figure.

What the comparison does **not** show: Chromium here is headless and draws no browser UI (tab strip, omnibox, sidebar), while Sweef's number includes painting its entire chrome through its own engine; Chromium renders far more of the web correctly. Do not quote the ratio without those caveats. Use `-skip-chromium` to omit it.
